# flyee.club — Platform monorepo

The PLATFORM of flyee.club: accounts, billing (Asaas for BRL, Stripe for USD, and Stripe for BRL too until Asaas is set up), entitlements, member token issuance with 30-day revalidation, the package-delivery API the `npx flyee` CLI consumes, catalog and release management, the member dashboard, admin consoles, per-segment metrics, the waitlist and the bilingual public site. The PRODUCT (the CLI, the harness core and the module contents) is a separate project that consumes this platform's API contract and module manifest; it never lives here. This repo has no link to any template: it was copied from the MedChina codebase on 2026-09-30 and is being reshaped into the platform phase by phase.

## Safety during the transition

- `apps/web/.env` is inherited and holds **MedChina production credentials** (Supabase, Asaas, Meta, GA4, AI keys). `apps/web/.env.local` blanks every one of them and must stay in place until the new flyee.club services exist. Next.js loads `.env.local` first, so the blank wins. A key the inherited file defines and `.env.local` does not is still read from the copy: `npm run preflight` names each one, and never prints a value.
- Never run `db:plan:remote`, `db:migrate:remote`, `db:gate:remote` or `test:db:remote` until `.env.local` points at the new flyee.club Supabase project. The gate (`scripts/remote-db-gate.mjs`) reads `.env.local` first, bootstraps an EMPTY project, and refuses a database it did not build (the MedChina one included, whose history names files this repo does not have), but do not lean on that.
- Never commit `.env`, `.env.local` or any other env file: `.gitignore` lists `.env` and `.env.*`, with `.env.example` as the one tracked reference. `.vercelignore`, at the root and in `apps/web`, lists the same two, because the Vercel CLI never reads `.gitignore` and a `vercel deploy` typed on a developer's machine would upload the inherited `apps/web/.env`. The deploy leaves only through the pipeline. Commit per plan phase, never push without being asked.

## Product (summary of docs/PRODUCT.md)

- **What it is**: a club called FlyeeClub, sold as a one-time access (the plan called "FlyeeClub") plus a subscription ("FlyeeClub Pro"). Members install the flyee harness in the AI they already use (Claude Code, Codex, Gemini CLI, Cursor) and keep receiving versioned tool modules and the updates that keep them working when the AIs change. The club never spends AI credit on the member's behalf.
- **Ladder** (prices are hypotheses stored as data in `plans`, never in code): the free rung (an account with no purchase, reached only through content; it installs the entry version of each app and is never sold or advertised) → FlyeeClub (tier `kit`: one-time, a year of catalog and updates counted from the paid invoice, renewed by buying again, card installments in BRL through Asaas, 1 device; what every CTA sells) → FlyeeClub Pro (tier `club`: monthly or annual: advanced lessons, recipes, meetings, roadmap vote, the "open the hood" depth, 3 devices) → mentoring and consulting, sold on demand through the contact form, never as plans. The former Pro family (`pro-*`) is inactive since migration 0025, kept for history. Every paid plan may be used in client projects; refunds go through support.
- **Delivery**: every plan also has one Claude Code session in the cloud, out of the device ceiling: the newest cloud session takes the place of the previous one and never a computer's (`plans.limits.cloud_sessions`, migration 0044, decided 2026-10-20). The dashboard issues the member token; `npx flyee` installs and updates from the platform's package server. Every update rotates the token; after 30 days without an update the member revalidates in the dashboard, which is where the next tier is offered. Installed tools keep working when access ends; only updates stop.
- **The member never uses the terminal** (decided 2026-10-08, built in 12.6): their AI runs every flyee command, and they only confirm in the conversation, approve the login in the browser and paste keys into a page the CLI opens. Where a screen or an e-mail needs something installed, it gives a sentence to paste into the conversation with the AI ("Instale o flyee seguindo flyee.club/instalar.md"), and the command appears beside it only as a reference. `/instalar.md` (`/en/install.md`) is the plain-Markdown page the AI follows: its text lives in the code, in both languages (`apps/web/src/lib/install-guide.ts`), with every command written the way one run by an AI needs it (`docs/CLI-CONTRACT.md`, 8.2).
- **Catalog**: one icon per module, filtered by seven stages (Planejar, Construir, Publicar, Divulgar, Vender, Escalar, Manter). The public store (the home and `/catalogo`) filters by store categories instead, the kinds of work of the home brief (Vender, Divulgar, Vídeo, Pesquisa, Construir): data edited in `/admin/catalogo` (`catalog_store_categories`, migration 0029), never in a manifest. The member area, the roadmap, the broad-use rule and the CLI API stay on the stages. Example: the video-editing app is in the stage Divulgar and the category Vídeo. Each app also carries the personas it is a good start for (`catalog_modules.personas`, migration 0032, marked in the console): the home brief's "Para quem é" block shows up to three published apps per persona (`lib/catalog/starters.ts`). Each module page carries a written guide in pt-BR and EN (how to use it, and the "open the hood" depth for FlyeeClub Pro), shipped inside each version's package at `guides/<pt-BR|en>/<usar|abrir-o-capo>.md` and shown for the version the member has installed, with an optional short video (unlisted YouTube); plus versions, changelog, declared permissions and checksum. Each app also carries its example of answering a request (`catalog_modules.showcase`, migration 0043, per language), written by the product and sent in its index: the home, `/catalogo` and each app page show the app answering it, never the command that installs it (decided 2026-10-17).
- **Metrics**: usage events only, never content, dimensioned by segment (`negocio`, `agencia`, `produto`, `dev`, `outro`: the public site's personas plus "other", migration 0028), AI tool and language. The focus segment is chosen by a data rule, not a date.
- **Free rung by version** (decided 2026-10-06, built in 12.5 on 2026-10-08 with one rule, option 1): entitlement is per version through channels (`@flyee/catalog/channels`, migration 0040). The free plan is on channel `free` and gets only the entry version of each app (`catalog_module_versions.is_entry`): the first published one takes the mark, the operator moves or clears it in `/admin/catalogo`, and a marked version is not yanked until the mark leaves it. Kit, membership and Pro stay on `latest`; the channel merges as a right, so the widest live source wins. The entry version is never updated because no new version enters `free`, not because of a block. The catalog answers `latest` per channel and `newest` for everyone, so the distance is visible in the CLI and in the dashboard. The module-wide free sample (`is_free_sample`) left the platform; the CLI API keeps the field, always false, because the CLI 1.x declares it.
- **FlyeeClub Pro is offered only inside** (decided 2026-10-08, phase 12: the public site's part is built since 12.2, the member area's since 12.4, `apps/web/CLAUDE.md`, "FlyeeClub Pro on the click"). The public site exists to sell FlyeeClub, the cheap one-time access: no public page names FlyeeClub Pro, shows its price or describes a feature only Pro has (recipes, meetings, proposing and voting, advanced guides, more computers), with or without a lock; `/planos` stays, with one plan; the terms of use keep describing both plans because they are the contract. Inside the member area Pro is offered on the click of a Pro feature, through one upgrade prompt, and a Pro control is never shown disabled. Unprompted, a FlyeeClub member sees it only on the home when use is broad (three or more stages in 30 days) and on the 30-day revalidation screen; an account with no purchase sees both offers, FlyeeClub ("Assinar", the current versions of the apps) and Pro, and keeps the Pro areas in its menu. A Pro area with nothing published, and an app that is planned but not built yet, carry the badge "Em breve". The founders offer was a MedChina concept and left the platform in 12.3 (migration 0038): no page shows a seats counter or a deadline.
- **The product repo** is `C:\AppsProjects\flyee`: the public npm package `flyee` (the CLI; 1.x supersedes an unrelated 0.7.x line the operator owns), the harness core bundled in it, and the apps, which are ZIPs uploaded to this platform, never npm packages. Its canonical harness file is `AGENTS.md` with `CLAUDE.md`/`GEMINI.md` pointers, and skills in `.agents/skills` bridged into `.claude/skills`. The first app is a video-editing app. On 2026-10-08 it held a finished, unpublished CLI 1.x, core 1.2.0 and five built packages (`video-analysis`, `video-render`, `video-studio`, `motion-carousel` 1.0.0 as the entry version and 1.1.0), all accepted by this platform's upload inspection; `docs/PLANO-IMPLEMENTACAO.md`, phase 12, lists what it still needs from here and what this platform asks of it. Another session works there: read it, never edit it.
- **Pipelines, compatibility and the MCP door** (decided 2026-10-06, phase 10, not built): a `workflow` app is a packaged pipeline whose automatic half runs locally without approvals and whose on-demand half takes the decisions; the platform never runs anything. The core keeps a declarative registry of AI tools with two tiers, "tested" (`compatible_ais`) and "compatible by the standard" (`AGENTS.md` + `.agents/skills`, reported as `other`, promoted by data). Every app ships an eval that also runs as a nightly canary. A read-only remote MCP server on the platform and a local one in the CLI are planned. Anti-resale (confirmed 2026-10-06): a signed per-download license binds the harness to the account and machine, generated files carry an opaque account mark, downloads are watched for anomalies, and the terms forbid redistribution; skills are never encrypted and installed apps never stop working.

## Golden rules

- **Platform, not product.** Never add CLI, harness or module logic here. The product exists in this repo only as the `/api/cli/*` contract and the module manifest schema.
- **Configurable data, never constants**: prices, plan limits, device ceilings, rate limits, grace windows, guarantee days and trial lengths live in `plans` and `platform_settings`.
- **The free rung is never offered.** No button, price column, badge or copy sells a free plan or a "free account" anywhere (no "Assine grátis", no "Criar conta gratuita"), and public pages never advertise free versions or free samples. The account with no purchase is the by-product of a sign-up that came from content (a video link carrying `origem`) or from the installer's no-login message; inside the member area it is described by what it is ("sem acesso à loja", "versão de entrada"), never as a named plan: the free plan's row in `plans` is the floor every account has, and its name is for the operator console only. `apps/web/src/lib/i18n/copy-rules.test.ts` fails on "grátis", "gratuito", "free" or "sem custo" in anything a visitor or a member reads, the waitlist answer aside ("sem custo extra" is allowed: it speaks of apps joining a paid access).
- **Copy rules** (decided 2026-10-07): no dash (— or –), exclamation mark or emoji in any text a visitor or member reads, in both languages (site, member area, checkout, e-mails, bell, CLI messages, legal texts; © and → stay), and none of the banned words (desbloqueie, potencialize, sem esforço, soluções inovadoras; unlock, elevate, empower, seamless, robust, supercharge, game-changing, "it's not just"). The operator console is exempt. Enforced by `apps/web/src/lib/i18n/copy-rules.test.ts`, pgTAP `0033_copy_rules` and the e2e text check (`.claude/rules/marketing.md`).
- **The member never uses the terminal** (decided 2026-10-08): no text a visitor or member reads tells them to run a command or to open a terminal. It says what to ask their AI. In the member area and the e-mails that is a sentence to copy, ending with the address of `/instalar.md` (`AskAiBlock`, `installGuideUrl`), with the command beside it as a reference (`REFERENCE_COMMAND` in `lib/install-links.ts`); on the site, a terminal frame is labelled as what the AI runs. A command an AI has to run is written in `/instalar.md` (`lib/install-guide.ts`, both languages) the way an AI needs it: `npx --yes`, `--json`, a time limit on what waits for the person, `add` with `--yes` after one plain sentence (the request is the yes, decided 2026-10-21). `lib/install-guide.test.ts` holds the page, the sentences and the reference commands together. The messages the CLI prints (`lib/cli/messages.ts`) speak to whoever runs the command, which is the AI.
- **Honest metrics**: `product_events` records usage, never content, through one allowlist of names and property values; segment, locale and AI tool are stamped from the profile on the server, never trusted from the client.
- Every mutation records an audit event (`recordAudit` in `apps/web/src/lib/audit.ts`). Every table has RLS, and every new migration states its grants explicitly.
- Visual identity changes ONLY in `packages/design-tokens/css/*.css`; run `npm run tokens:generate` and commit `tokens.generated.ts` with it.
- npm workspaces: install dependencies from the root (`npm install`), never inside an app.
- Icons: Phosphor through the tsconfig alias `@/icons/nexture/*` → `src/icons/phosphor/*` (fallback stubs re-export Nexture). App icons are the exception (decided 2026-10-17): an app's tile draws the ORIGINAL Nexture glyph its operator names, through `src/icons/app-glyphs.tsx`, so an app never looks like a control (`.claude/rules/icons.md`).
- **MUI X through its free packages only** (decided 2026-10-14, as MedChina does): no Pro or Premium package and no licence key in any environment. A feature that only a paid package has (pinned columns, row grouping, a range picker, a funnel chart) is built as the platform's own component, never by installing the package. Enforced by `apps/web/src/lib/mui-x-free.test.ts`.
- Fonts: Mulish (`--font-body`), Londrina Solid (`--font-heading`; `font-display` falls back to it) and JetBrains Mono (`--font-mono`). Londrina Solid has two weights, Regular and Black: Black (`font-bold`) for the display scale and headings from 24px up, Regular (`font-normal`) below that.
- The dark band (footer, deep sections, terminal bodies) is `bg-background-deep`, never the dark primary: it has to stay dark under any palette.
- Red is reserved for risk and failure.
- **The yellow is a fill, never a foreground on a light ground** (WCAG 2.2 AA, decided 2026-10-08; it measures 1.5:1 on white). A label or icon on a primary fill is `text-primary-contrast` (the logo's charcoal), never white; the primary as text, link, icon, focus ring or checked control is the ink (`text-primary-ink`, `ring-primary-ink`, `outline-primary-ink`), charcoal in light mode and yellow in dark. Bare `text-primary` belongs only on the deep band and other grounds that are dark in both modes. Enforced by `apps/web/src/lib/palette-contrast.test.ts`; the reasoning and the ratios are in `docs/DESIGN.md`, palette usage.

## Commands (root)

- `npm run dev` / `build` / `start` / `lint` / `lint:fix` / `prettier` — delegate to `apps/web`.
- `npm run typecheck` — `apps/web` with its pinned TypeScript 5.8. Never run a bare root `npx tsc` on apps/web: it picks the hoisted TS 6.
- `npm run test` — the script tests (`test:scripts`), the package tests (`@flyee/ai`, billing, catalog, e-mail) and the web vitest suite. `npm run test:e2e` / `test:a11y` — Playwright against a production build.
- `npm run ci:verify` — everything CI runs: harness checks, MUI class check, typecheck, tests, build.
- `npm run preflight -- --stage waitlist|open [--target preview] [--file <env file>]` — what an environment still lacks for a stage, by name and never by value. Without `--file` it reads `apps/web/.env.local` over `apps/web/.env`, as the app does; with the file `vercel env pull` wrote, a Secret that did not come back is reported as not read (`?`). No network, no database (`docs/DEPLOY.md`, "Roteiro da abertura").
- `node scripts/prune-messages.mjs --check|--write|--list` — message catalogs without unused or missing keys (pt-BR is the reference).
- `npm run test:db:embedded` — migrations + pgTAP on an embedded PostgreSQL 17, no Docker (first run installs it into `.cache/`). `npm run db:start` / `db:stop` / `test:db` — the same through local Supabase (needs Docker). The `db:*:remote` scripts are gated: see "Safety during the transition".
- `npm run db:schema:pull` — regenerate the Drizzle mirror from the migrations.
- `npm run tokens:generate` — regenerate the TS token mirror.

## Platform decisions

- Deploy: Vercel, only through GitHub Actions (`docs/DEPLOY.md`). Database, auth and storage: Supabase (Postgres + RLS). ORM: Drizzle. Email: Resend. Jobs and cron: Inngest. Billing: Asaas for BRL (PIX, card, Asaas issues the NFS-e) and Stripe for USD, routed by the purchase currency. Until Asaas is set up, Stripe charges BRL too (decided 2026-10-12, `BILLING_BRL_PROVIDER=stripe`): no card installments, PIX only on Stripe's own page, the NFS-e issued outside the platform, the CPF/CNPJ still asked in the checkout (`docs/BILLING.md`, "Moeda e provedor").
- Locales: pt-BR (default) and en, hybrid since phase 7.1: the public site lives under `app/[locale]` with next-intl `pathnames` (pt-BR at `/`, English at `/en` with translated paths, both indexed with hreflang), while dashboard, admin, auth and checkout keep the cookie and profile locale.
- Guides are written and travel in each version's package (migration 0030, `docs/CLI-CONTRACT.md` §7), read through `can_read_guide`; the optional video of a guide is an unlisted YouTube video gated by the page and by RLS (`can_watch_lesson`). Meetings use an external link (Zoom/Meet), with registration and click-through recorded on the platform.
- Do not introduce Cloudflare-specific services (Workers, D1, R2, Workers AI).
