# flyee.club web (apps/web)

Next.js 15 (App Router) + React 19 — the only app of the flyee.club platform: public site, member dashboard, checkout, admin consoles and the CLI delivery API. See the root `CLAUDE.md`, `docs/PRODUCT.md` and `docs/PLANO-IMPLEMENTACAO.md`.

> The database is the baseline in `packages/db/migrations` (`0000`–`0018`, plus the migrations added since, described in `packages/db/README.md`). Prefer the function name when searching for a rule.

## Stack and conventions

- **UI**: MUI v9 is the base. Before building a component, look for a MUI or MUI X equivalent (installed: Data Grid + Pro, Charts + Pro, Date Pickers, Tree View, Lab). Icons: **Phosphor** through the `@/icons/nexture/*` tsconfig alias (real adapters plus Nexture fallback stubs, see `src/icons/README.md`); never import an icon library directly. Import the one icon you render; `src/icons/icon-registry.tsx` (icons by NAME, for the dashboard menu and catalog icons) imports the whole set and ships all of it to any client component that imports it.
- **Styling**: MUI theme driven by CSS variables (`hsl(var(--token))`) from `@flyee/design-tokens`. Component overrides live in `src/style/**/*.css` inside CSS layers (`theme, base, mui, components, utilities`). Tailwind 4 for layout utilities, merged with `tailwind-merge`. Run `npm run check:mui-classes` after touching `src/style/**`.
- **Themes**: one locked palette (`theme-orange`, provisional) × light/dark, as classes on `<html>`. The tokens are scoped to those classes, so the root layout renders them on the server (the palette and the default mode) and a script in `<head>` corrects the mode before the first paint for a browser that stored another choice; `src/theme/theme-provider.tsx` keeps them in sync afterwards and applies only a palette listed in `THEME_OPTIONS` whatever a browser has stored. Never leave the classes to a client effect again: until it ran, the page had no palette at all. Fonts: Mulish (`--font-body`), Londrina Solid (`--font-heading`; `font-display` falls back to it) and JetBrains Mono (`--font-mono`, every `<code>`/`<pre>` and `font-mono`). Londrina Solid ships Regular and Black only: MUI `h1`/`h2` and the display scale are Black, `h3`–`h6` and any heading under 24px are Regular (`font-normal`).
- **Forms**: Formik + Yup. Semantic data (phone, CPF/CNPJ, CEP, money) uses `components/product/fields/*`, never a raw `TextField`; persist digits, never masks.
- **i18n**: next-intl; every user-facing string goes through messages. Locales `pt-BR` (default) and `en`; catalogs in `packages/content/messages/`. `src/lib/i18n/messages.test.ts` pins key parity, no blank values and identical ICU placeholders. `node scripts/prune-messages.mjs --check` fails on keys no code renders and on keys the code renders that the catalog lacks. Namespaces: `marketing` (public site), `auth`, `product` (member dashboard, billing, settings), `dashboard` (chrome and menu). The home's copy lives in `components/marketing/home-copy/{pt-BR,en}.ts`; `pt-BR.ts` is the structural source of truth (`HomeCopy = typeof homeCopyPtBR`); the text follows `docs/HOME-COPY.md`, the home copy the product owner delivered.
- **Admin copy is hardcoded pt-BR**, outside i18n: the operator surface has one reader. Code comments stay in English; a database value (enum, slug, status) is mapped to a label, never shown raw. `components/data-grid/data-table.tsx` takes its grid chrome from MUI X's own locale pack.
- **Which language a request is in** depends on the kind of page, and `i18n/request.ts` is the one place that decides it:
  - **Public site: the URL.** Pages live under `app/[locale]/` (Portuguese at `/`, English at `/en` with translated addresses) and are declared in `src/i18n/routing.ts` (next-intl `pathnames`, `localeDetection: false`). The middleware runs next-intl only for those addresses (`matchPublicPath`), merging the refreshed Supabase cookies into its rewrite, and persists the URL language in the locale cookie so sign-in and the app that follow continue in it. Internal links use `LocaleLink`/`localizeHref` with the Portuguese path; `app/[locale]/layout.tsx` repeats the `NextIntlClientProvider` because the root layout is not re-rendered by a client-side navigation; the public language switch is a full page load. A browser that reads the other language gets an offer (`language-suggestion.tsx`), never a redirect.
  - **Everything else (sign-in, member area, checkout, admin): the visitor.** `lib/locale-request.ts` (`resolveRequestLocale`): the cookie is the visitor's choice and always wins; otherwise `lib/locale-detection.ts` decides from `Accept-Language`, then Vercel's `x-vercel-ip-country`. Three rules are load-bearing: detection happens at RENDER time, not only in the middleware (a cookie set by the middleware lands on the response); a crawler is never switched (`isCrawler`); an automatic switch is always announced (`COOKIE_KEYS.localeAuto`). The in-app switch (`setClientLocale` in `i18n/locale.ts`) also writes `profiles.locale` through `update_member_profile`, outside support sessions; a new browser does not read the profile yet (detection decides until the member switches).
- **Path alias**: `@/*` → `./src/*`. **Brand**: identity comes from `@flyee/content` (`src/brand.ts` re-exports it); the logo is the single component `src/components/logo/logo.tsx`, which references the official SVGs in `public/brand/` (light-surface and dark-surface files; `tone="contrast"` on the deep band) and never redraws them. The favicons, the square mark and the home-screen tile are generated from the mark: `npm run brand:assets`.
- **Remote data**: `lib/remote-state.ts` (`RemoteState<T>`: idle, loading, success, empty, error). An error is never rendered as empty.

## Member dashboard (product layer)

- Routes: `/inicio` (`DEFAULTS.appRoot`), `/modulos` and `/modulos/[slug]` (the dashboard catalog is `/modulos` because the public one is `/catalogo`), `/receitas` and `/receitas/[slug]`, `/novidades`, `/encontros` and `/encontros/[slug]`, `/roadmap`, `/settings` (profile and avatar, segment, AI tool, language, timezone, credentials), `/settings/security` (2FA, sign-in history), `/settings/devices` (machines, revalidation dates, disconnect; `/settings/connections` redirects here), `/settings/billing`, and `/onboarding` (outside the dashboard shell).
- **Screen shape**: `page.tsx` is a server component that reads with the member's session through `lib/member/*` (`getMemberContext()` gives the session client, workspace, language, currency and `org_entitlements`; the catalog comes from `lib/catalog/read.ts`, shared with the CLI API) and hands a `state` (`ready` | `error` | `unavailable`) to a client view that takes plain props. An error is never rendered as an empty state, and every write goes through `lib/member/actions.ts` to the database function that owns the rule.
- **Lessons**: the video id is only returned by the database when `can_watch_lesson` allows it, so a missing id is the lock; the player loads youtube-nocookie on play and records `lesson.started` / `lesson.completed`.
- **Offers** (`lib/upsell.ts`, `decideUpsell`): no access → kit; a machine that reported a client's project → Pro; the kit used across three or more trails in 30 days → membership. The card (`UpsellCard`) appears on the home and on the CLI revalidation screen, says why it is there and shows the price from `plans`; the billing webhook records `upsell.purchased` when a purchase follows a card seen in the last 14 days.
- **Activation** (`lib/onboarding.ts`): four steps with LIVE predicates, never click tracking — profile (segment, AI tool, language) → access (kit or plan) → install (`npx flyee login`) → first run (closed by the CLI's first `tool.executed`). The facts come from the definer RPC `member_activation_facts()`. `isActivated` = a device AND a first execution. `resolvePostAuthDestination` (called by sign-in, sign-up, `/auth/callback` and `/auth/two-factor`; never from the middleware) sends a member to the `/onboarding` wizard only while the profile questions are unanswered; the later steps are the home's checklist.
- **Entitlements**: `hooks/use-entitlements.ts` calls `org_entitlements(org)`, the single answer to what a workspace may use: the free floor, live grants (the kit, licenses, courtesies), the live subscription with its add-ons, and an unconfirmed PIX inside its window, merged so more sources never mean fewer rights, with the tier and the sources named. Screens branch on it, never on plan names. `org_has_entitlement(org, key)` is the yes/no form for policies and gates. `components/product/gate-notice.tsx` renders the gate states (`available`, `loading`, `unknown` with retry, `blocked` with a reason). `components/layout/menu/plan-indicator.tsx` shows the tier and the upgrade path.
- **Sign-up**: one person is one account. `handle_new_user` creates the profile AND the personal workspace from `display_name`; the sign-up metadata also carries `locale` (the phase 2 trigger reads `display_name`, `segment`, `ai_tool`, `locale`). `/auth/complete-profile` is only the safety net for an account without a workspace.
- **Usage events**: the browser reports only offers shown and clicked (`trackOffer` in `lib/product-events.ts`, which terminates the PostgREST builder with `.then()`: a bare `void supabase.rpc(...)` never sends the request). Everything that counts toward a metric is written by the backend with `trackServerEvent` (`lib/product-events-server.ts`). The database stamps segment, language and AI tool from the profile and drops any property outside its allowlist.
- Reusable blocks live in `components/product/*` and are listed in `components/product/catalog.json` (injected by the `product-screen-guard` hook). Every zero-data view uses `EmptyState`.

## Public site (marketing layer)

- Routes in `src/app/[locale]/(marketing)/`, each in Portuguese and English: home `/` and `/en`, `/como-funciona` (`/en/how-it-works`), `/catalogo` and `/catalogo/[slug]` (`/en/catalog/...`), `/planos` (`/en/pricing`), `/sobre` (`/en/about`), `/contato` (`/en/contact`), `/ajuda` (`/en/help`), `/blog` (`/en/blog`), `/espera` (`/en/waitlist`), `/verificar/[ref]` (`/en/verify/...`, `noindex`), `/legal/{termos,privacidade,cookies}` (`/en/legal/{terms,privacy,cookies}`). Campaign pages live in the sibling group `src/app/[locale]/(funil)/`, whose layout drops the site menu and keeps the trackers, the cookie notice, the support widget and a legal-minimum footer: `/fundadores` (`/en/founders`, `noindex`), the founders price with the seats and deadline of `founders_offer()` and a page per closed reason. A new public page is declared there (both addresses; that is also what makes it public to the middleware), enters `src/app/sitemap.ts` when indexed (once per language, with alternates), and spreads `publicPageMetadata({ path, locale })` from `lib/seo.ts` into its `generateMetadata` (canonical, hreflang with `x-default`, Open Graph URL).
- ONE design system: pages compose the primitives in `src/components/marketing/` (`Section`/`Container`/`SectionHeader`, Hero, FeatureRows, RuledGrid, ProcessSteps, StoreGrid, AppStorePreview, BentoGrid, StatBand, PricingSection, Faq, Cta), listed in `components/marketing/catalog.json`. The inherited Landing DS is gone. `docs/DESIGN.md` holds the committed direction (the palette is provisional): no palette hue on small text, hues ride on icons, bars and fills.
- **No loading boundary above the public pages**: neither an `app/loading.tsx` nor a `<Suspense>` in the root layout. A boundary there starts the response before a page can call `notFound()` or `redirect()`, so a missing app answered 200 with `noindex` and a moved address got a meta refresh. Each signed-in area keeps its own boundary in its layout. The public 404 is `app/not-found.tsx` (marketing namespace, leads back to the site); the member area has `app/(dashboard)/not-found.tsx`.
- **The loader overlay is for the signed-in areas only.** `#initial-loader` (root layout, `public/initial-loader.{css,js}`) covers the page until the window load event, while the shell settles. A public page arrives complete and styled, so the root layout leaves the overlay out (`isPublicPageRequest()` in `lib/locale-request.ts`): with it, a phone showed a white screen for seconds over content that was already painted. Anything a public page decides in the browser and shows above the fold must be decided before the first paint, from `<head>` (the mode class, the language offer of `lib/language-offer.ts`), never after hydration. Next serves a 404 thrown by a page as an error document that React builds in the browser, which never runs the loader script; `InitialLoaderGuard` lifts the overlay there.
- **Performance of the public site** (measured 2026-10-01, Lighthouse, production build): desktop 93 to 98, mobile 52 to 67, SEO 100. What a public page still pays on a phone is the shared shell: MUI and its styling engine hydrate on every page (three whole-document restyles at start-up) and one 382 KB stylesheet carries the overrides of every dashboard component. Getting the mobile score to 90 means a public shell without them, which is a decision, not a fix (`docs/PLANO-IMPLEMENTACAO.md`, phase 7). Do not add to that cost: no scripted animation, no client component where a server one does, one icon import per icon.
- **Public catalog** (`src/lib/catalog/public.ts`): `/catalogo`, the module pages, the numbers of the home and the module half of the sitemap read published rows with the anonymous client through the same reader as the CLI API (`lib/catalog/read.ts`). A module whose name has no English text stays out of the English pages and sitemap, and its English address leads to the English catalog; an unreadable catalog renders a "could not load" state, never an empty catalog.
- **Visits per entry door** (`src/lib/site-views.ts`): the middleware counts each document load of a public page by someone not signed in (never a crawler, a prefetch, a redirect or a client-side navigation) through `count_site_view`, after the response (`event.waitUntil`); the door is the link's `?origem=`, else the first-touch door. These are the visits of the entry doors table in `/admin/metricas`.
- `/ajuda` and `/blog` render DB-managed content (written in `/admin/help` and `/admin/blog`) through `src/lib/public-content.ts` (anon client, published rows, only in the language of the address: translations are rows linked by `translation_group`, and a slug of the other language redirects to its translation or to the section index); Markdown renders via `components/marketing/markdown-prose.tsx` (raw HTML ignored).
- **Legal pages render `consent_terms`** (`components/marketing/legal-document.tsx` over `lib/legal.ts`): the version in force of `terms`, `privacy` and `cookies` in the language of the address, with version and date, so the page shows exactly the text people accept. When the text cannot be read the page says so; the catalogs hold no second copy of the terms.
- **Launch stage** (`lib/launch.ts`, `platform_settings.launch`, migration 0019): in `waitlist` (the seed, and the fallback for anything unreadable) every primary CTA of the public site leads to `/espera`; in `open` they lead to sign-up and checkout. Sign-in and sign-up stay reachable in both. The superadmin flips it at `/admin/support`, which also holds the operating company printed in the footer (`legal_entity`, read by `getLegalEntity`): the terms identify the operator "in the site footer".
- **Waitlist** (`/espera`, `/en/waitlist`): `espera/actions.ts` validates (honeypot, consent), calls `submit_lead` with the service role (first-touch campaign from the attribution cookie, network window keyed by an HMAC of the IP with `PUBLIC_FORMS_IP_SALT`), and e-mails the double opt-in link (`sendLeadConfirmationEmail`, in the language the address signed up in). The answer never reveals whether an address was already listed. The link `/espera/confirmar?t=` is rewritten by the middleware: the token moves into an httpOnly cookie (`COOKIE_KEYS.leadConfirm`) and the page loads at the clean address, because analytics scripts and Referer headers carry URLs; confirming takes a button press, because mail scanners open every link. `lib/lead-jobs.ts` runs `purge_expired_leads` daily (unconfirmed addresses go after 7 days, as the page promises).
- Pricing reads plans through `@flyee/billing/public` (`listPublicPlans`, read-only) with i18n placeholder plans as fallback; the contact form sends through `@flyee/email` (`CONTACT_FORM_TO`).
- Display type: `font-display text-display-{2xl,xl,lg,md}` (fluid clamp scale from `@flyee/design-tokens/css/marketing.css`). Motion: CSS first (the hero entrance in `style/layout/marketing-motion.css`, `<Float>`, the `<Reveal>` transition started by `watchEntry` in `components/marketing/motion.ts`); GSAP is loaded only by `<Parallax>`, on demand, and never in admin code. Transform + opacity, honors `prefers-reduced-motion`, nothing runs forever.
- Tracking (`docs/TRACKING.md`): the marketing and funnel layouts render the Meta Pixel and GA4 server-side; the member area loads the same snippets after the page is interactive and never on `/admin` (`components/consent/dashboard-trackers.tsx`); one opt-out cookie and one notice cover both (`lib/analytics.ts`, `CONSENT_VERSION` 4, privacy and cookie policies version 2 in migration 0022). Sign-up, checkout and purchase conversions also go server-side (`lib/meta-capi.ts`, `lib/ga4-mp.ts`). The snippets are written once in `lib/tracker-snippets.ts`.

## Billing and checkout

- `/settings/billing` (the ladder in the member's currency, current subscription, cancel with a reason and undo, invoices, billing profile, pending checkout, payment recovery) and `/assinatura?plan=<slug>` (the focused checkout; without `plan` it opens the kit in the visitor's currency; Pix, card or installments in BRL, Stripe Checkout in USD). Server actions in `settings/billing/actions.ts` (checkouts), `actions-cancel.ts` and `actions-recovery.ts`, sharing `billing-server.ts`; provider webhooks at `api/webhooks/[provider]/route.ts`, idempotent through `claim_billing_webhook_event`/`complete_billing_webhook_event` with an attempt ceiling.
- **Dunning grace**: `past_due` keeps access for a configurable window (`platform_settings` key `dunning`) counted from `subscriptions.past_due_since`; `billing_past_due_grace_ends()` is the one answer every gate shares. Installed tools always keep working; only updates stop.
- **Comped plans**: `set_org_plan(org, plan, note)` puts a workspace on a tier without checkout (betas, partners, the team). It updates the live row instead of inserting, keeps the period bounds NULL, refuses a provider-backed subscription (`provider_managed`) and stamps `self_grant` in the audit event when the operator comps their own account.
- The founders offer counts real seats (`lib/founders-offer.ts`); the guarantee window comes from `platform_settings` (`lib/guarantee.ts`); a pending PIX survives a closed tab (`lib/pending-pix.ts`).
- **Entitlements**: `org_entitlements(org)` is the one answer (free floor + live grants + live subscription + add-ons, with `tier` and `sources`). Screens read it through `hooks/use-entitlements.ts` and `@flyee/billing/entitlements`, never by plan name or slug. The kit is an `entitlement_grants` row the webhook creates on the paid invoice; CLI tokens are revoked only when catalog access really ends (`lib/billing-lifecycle.ts`).
- **Currency**: `?moeda=` (kept in a cookie by the middleware) or the page language picks BRL or USD (`lib/billing-currency.ts`), and the plan's currency picks the provider. A yearly BRL plan split into installments is ONE purchase that does not renew; so is the kit, which may also be split (`lib/payment-choice.ts`) and whose grant is keyed by the installment, not the parcel. The kit lasts `plans.access_months` from the paid invoice; buying it again chains a new term after the current one, the end is announced 15 days ahead and settled by the daily billing job (`lib/billing-notices.ts`). Full design, state machine, refunds and deferred items: `docs/BILLING.md`.

## Platform admin and account

- Superadmin area at `src/app/(dashboard)/admin`: `layout.tsx` is a server gate on `profiles.is_superadmin` (RLS stays the real defense); the Admin menu group renders only for superadmins (`hooks/use-is-superadmin.ts`). Consoles: `/admin` (the counters of `admin_metrics()` and a tile per console), `/admin/membros`, `/admin/metricas`, `/admin/catalogo` and `/admin/catalogo/[slug]`, `/admin/roadmap`, `/admin/encontros` and `/admin/encontros/[id]`, `/admin/leads`, `/admin/billing`, `/admin/ai` (model price book), `/admin/audit` (audit trail + sign-in log), `/admin/insights`, `/admin/backups`, `/admin/announcements`, `/admin/help`, `/admin/blog` (posts and member news, with audience and translation links), `/admin/support`. `/admin/organizations` redirects to `/admin/membros`.
- **Console shape** (phase 6): `page.tsx` is a server component that reads through `lib/admin/*` inside `loadConsole()` (`lib/admin/session.ts`: the operator's session, `ready | error | unavailable`, so a failed read is never an empty list) and hands plain props to a client view; writes are server actions in the console's `actions.ts` that call `requireSuperadmin()` again (a server action is a public endpoint) and record an audit event; the database function that owns the rule is the one doing the write wherever one exists. Formatting is `lib/admin/format.ts` (pt-BR, Brasília clock, money per currency, never summed) and every database value becomes a word through `lib/admin/labels.ts`.
- **Members** (`/admin/membros`, `admin_members_overview()` / `admin_member_dossier()`, migration 0015): the tiles are the filters and count the same flags the rows carry (`lib/admin/members.ts`). The dossier (row click) reads the account, its entitlements, money, machines, usage, consents and first touch. Actions: support access, disconnect every machine (`revoke_member_tokens`), reset 2FA, the superadmin role, ban (also revokes the CLI tokens: the token server is ours, not the auth provider's) and account deletion; ban, 2FA and deletion need `SUPABASE_SERVICE_ROLE_KEY`. A second tab lists people without a workspace.
- **Metrics** (`/admin/metricas`, `admin_segment_weekly()` with payers per currency and `admin_door_weekly()`, migrations 0015/0021): the focus rule (`focusRule` in `lib/admin/metrics.ts`) is the docs/PRODUCT.md proposal read as an indicator: a segment leads kit purchases, 7-day activation and weekly use for 4 COMPLETE weeks, comparing only the four focus segments with at least 30 accounts with access; `outro`, an unanswered segment and the running week never count; a tie or a blank week leads nobody. Windows still open (activation 7 d, kit to membership 60 d) are marked, never estimated.
- **Catalog** (`/admin/catalogo`): modules, recipes, trails (texts only: the seven slugs are fixed) and the delivery settings (`platform_settings.cli`). A module's page uploads the ZIP through the two-step upload of phase 3, then publishes, marks stable, yanks with a public reason or discards a draft (`lib/catalog/version-actions.ts`, `discardDraftVersion`); lessons keep the video id apart (`catalog_lesson_videos`). Usage per module and version comes from `admin_catalog_stats()` (migration 0021).
- **Meetings** (`/admin/encontros`): the lifecycle rascunho → inscrições → ao vivo → encerrado → arquivado, the page in both languages, the private room and recording links (`meeting_links`), results (`meeting_results`) and registrants (`admin_meeting_registrants`). The e-mails card shows how many registrants each of the four messages reached (confirmation, 24-hour reminder, last-hour reminder, recording) and sends one now, only inside its window (`meetingEmailWindow`), to whoever has not received it.
- **Leads** (`/admin/leads`): status tiles (confirmed, waiting, opted out), opt-out, erasure (`purge_lead`) and an export of confirmed, not opted-out contacts as a Resend contact CSV, audited. The newsletter consent covers e-mail sent through Resend only, so there is no ad-audience export. "Escrever para a lista" writes a message per language (Markdown), shows who would receive it before sending, and delivers it in batches (`newsletter_sends`, `lib/newsletter.ts`); a send that stopped is resumed from the same screen and never repeats a reader. Without an e-mail provider the screen says so and the button is off.
- Every mutation records an audit event through `lib/audit.ts` (`recordAudit`). Sign-ins are logged by a database trigger; members see their own in `/settings/security`.
- **Granting the superadmin role** (`set_user_superadmin(user, value, note)`): the flag is fenced by a trigger on `profiles` keyed on WHO is asking (`is_superadmin()` reads the database), because a self-`PATCH` of `is_superadmin` would otherwise promote any signed-in user. Self-change is refused in both directions. A session with no JWT (service role, migration, psql) passes: that is how the first superadmin is made.
- **Support impersonation** (`lib/impersonation-actions.ts`, started from `/admin/membros`, which a visit returns to): the operator works inside a member's account through a **parallel session cookie** (`@flyee/auth` `authCookieName`), so leaving deletes a cookie and never strands the operator. Load-bearing: the write fence is in the DATABASE (`is_impersonated()` matches the JWT `session_id` against `impersonation_sessions`; triggers refuse member-owned writes), and it never expires; ending a visit uses `signOut({ scope: "local" })`, never the global default; starting requires the operator's own session at AAL2; credentials and `/admin` are blocked in the middleware. A reason is required, the member is notified, and the access is labelled as support in their sign-in history. Duration lives in `platform_settings` (`impersonation`).
- **Account deletion** (`admin/membros/components/delete-account-dialog.tsx`, server action `deleteAccount`, RPC `admin_delete_account(user, confirm_email, reason)`): the unit is the account plus every workspace it alone belongs to. The order is fixed: re-read the preview, cancel any live provider subscription (a failure deletes nothing), run the RPC in one transaction (it deletes rows that hold data through NO ACTION/RESTRICT references first, holder before held, and purges `record_versions`), then remove storage files through the Storage API using `admin_orphaned_account_storage`, which refuses anything still alive. Refused in the database: yourself, any superadmin, a support session, a live provider subscription. The audit event `admin.account.deleted` survives with counts only.
- **AI spend** (`lib/ai-spend.ts`, price book at `/admin/ai`): every provider call records one `ai_spend` row through the `ChatProvider` `onUsage` sink. Prices are configuration (`platform_settings` key `ai_prices`, per million tokens), shipped empty; an unpriced model reports `priced = false`, and consoles show the unpriced count beside every total. Cost is stored in USD micros and converted only with an operator-set rate.
- `/admin/insights` (`api/admin/insights/route.ts`): the model writes SQL from an `information_schema` catalog and each statement runs inside a `read only` transaction with a 5 s `statement_timeout`. **The read-only transaction is the safety boundary, not the prompt.** Every executed query is audited and shown. Needs `DATABASE_URL` and one AI provider key.
- **Monday digest** (`lib/admin-jobs.ts` over `lib/admin/weekly-digest.ts`, Inngest cron at 08:30 Brasília): last complete week's five focus metrics per segment, the focus rule and the accounts that need someone (past due, cancellation scheduled, no update for 25 days, no machine), as one bell notification and one e-mail (`sendAdminWeeklyDigestEmail`) per superadmin. Nothing to report means nothing is sent; `notifications.source_key` (`admin-weekly:<week>`) makes it idempotent per week.
- `/admin/backups` (`@flyee/backup`): nightly cron plus "Run backup now" (inline fallback without Inngest). Archives land in the private `backups` bucket; downloads are signed URLs.
- Account plumbing is real: the header bell reads `notifications` (create rows server-side with `lib/notifications.ts`), announcements render in the dashboard layout with per-user dismissal, `/settings` edits the profile (avatar in the `avatars` bucket) and credentials. The quick-support widget (`components/support/support-widget.tsx`) reads the channels from `platform_settings` (`support`, edited at `/admin/support`), falls back to `BRAND.support`, and renders nothing until a human channel exists.

## Messages: bell, e-mail and scheduled jobs

- **Every message to a member is written in the reader's language**, chosen when it is written: `profiles.locale` for members, `leads.locale` for contacts of the list. Bell texts are stored text, so `notifyLocalized` (`lib/notifications.ts`) groups the recipients by language and takes the words from `lib/messages/bell-copy.ts`; e-mail copy lives in `packages/email/src/copy/{pt-BR,en}.ts`. Both are typed against the Portuguese object, so one language cannot gain a line the other lacks. Never write a member-facing sentence at a call site. The operator's own digests stay in Portuguese.
- **A plan is called by `plans.name`**, never by a word in the copy. A date and an amount arrive already formatted for the reader (`lib/messages/format.ts`: the reader's time zone, `America/Sao_Paulo` when unknown). A sentence that states a time ("within 24 hours") must be true anywhere inside the window the message is sent in (`lib/meeting-email-kinds.ts`).
- **Claim, then send.** A job that writes to people may run twice. The database marks the row in the statement that returns it (`claim_token_reminders`, `claim_term_end_notices`, `claim_meeting_emails`, `claim_newsletter_batch`, migration 0023) and only then the message leaves. Where there is no row to mark, the bell's unique `source_key` is the fence (the welcome, the weekly summary) and the e-mail goes only to who got a NEW bell row. A message may be lost to a failed send, never sent twice. A batch the provider refuses is given back (the meeting columns, `settle_newsletter_batch`), so the next run tries it again.
- **Without `RESEND_API_KEY` nothing breaks**: senders return `{ sent: false }` with no error, the bell still rings, and a job does not claim what exists only as e-mail (a meeting confirmation, a batch of the list). Without Inngest, what an action starts runs in the request (`requestMeetingEmails`, `startNewsletterDelivery`), and nothing scheduled runs.
- **What a reader can stop**: only the weekly summary (`profiles.marketing_email_opt_out`, the switch in `/settings`) and the messages to the list (`leads.opted_out_at`). Those carry `unsubscribeUrl(...)` in the body and as `List-Unsubscribe` (one click). `/api/public/email/unsubscribe` acts on POST only; a GET moves the request into an httpOnly cookie and lands on `/descadastro`, which asks with one button, because mail scanners open every link they deliver. Receipts, notices about the account and the reminders of a meeting someone registered for ignore the preference.
- **Jobs** live in `lib/*-jobs.ts` and are listed in `app/api/inngest/route.ts`; a function missing from that list never runs. `token-jobs` (a connection about to expire), `updates-digest-jobs` (weekly: only versions published that week, only machines with a live connection; the rule is `pendingUpdates` in `lib/updates-digest.ts`), `meeting-jobs` (a 10-minute sweep of `due_meeting_emails`, plus the event sent by a registration and by the buttons of `/admin/encontros`), `billing-jobs` (settlement, maintenance, the end-of-term notice), `newsletter-jobs` (one step per batch of 100), `maintenance-jobs` (event rollup, purges, staged uploads), `lead-jobs`, `admin-jobs`. Schedules are listed in `docs/DEPLOY.md` ("E-mails e jobs").
- **Billing notices** go through `lib/billing-notices.ts` and never throw: by the time one runs the database is already right, and a webhook that failed on a bell would be replayed by the provider and reconcile the whole event again (`docs/BILLING.md`, "Avisos ao integrante").
- **Auth e-mails** (confirmation, password recovery, e-mail change) are sent by Supabase, not by the app: `supabase/templates/*.html`, bilingual by the `locale` the sign-up writes in the account's metadata. They are not rendered by any test here; `docs/DEPLOY.md` has the manual check.

## Auth

- Supabase through `@flyee/auth` (`client`/`server`/`middleware`/`service`). `src/middleware.ts` refreshes the session and protects everything except the public pages (`matchPublicPath`, from `src/i18n/routing.ts`) and `PUBLIC_PREFIXES`. Without `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` the middleware no-ops and the auth screens show a configuration hint.
- 2FA (TOTP): enrolled at `/settings/security`; the middleware forces the AAL2 step-up at `/auth/two-factor`.
- Internal redirects go through `lib/safe-next.ts` (`sanitizeInternalNext`), never a raw `next` parameter.
- **CLI token server** (`lib/oauth/*`, `docs/CLI-CONTRACT.md`): one first-party public client, `flyee-cli`, seeded in migration 0010; no dynamic registration. Browser login with PKCE and a loopback redirect on any port (`lib/oauth/redirect.ts`), device authorization (`/api/oauth/device` + `/ativar`, `lib/oauth/device-code.ts`), revocation (`/api/oauth/revoke`). Opaque tokens, one family per machine (`device_id`), access 1 h, refresh 30 days rotated on every use: an expired refresh answers `invalid_grant` with `error_uri` = `/revalidar`, and a login on a machine that held a chain before renders the revalidation screen. Logins, revalidations and expired refreshes are product events (`cli.login`, `token.revalidated`, `update.denied_token_expired`).
- **Delivery API** (`app/api/cli/*`): every handler runs inside `runCliRequest` (`lib/cli/gates.ts`), which checks token → scope → `org_entitlements` (read on every call) → `X-Flyee-Device` → `cli_rate_allowance`, answers refusals as `{ error, message (member's language, lib/cli/messages.ts), action_url }` and files each call in `cli_requests`. Downloads are 300-second signed URLs from the private `modules` bucket; the CLI verifies size and SHA-256. Catalog reads live in `lib/catalog/read.ts`, shared with the member dashboard.
- **Packages**: `lib/catalog/package.ts` inspects a ZIP (safe paths, size ceilings, manifest `files` equal to the archive); `lib/catalog/upload.ts` turns a staged upload into a draft version; `lib/catalog/version-actions.ts` publishes, marks stable and yanks (superadmin, audited).

## Watch out

- `src/style/global.css` imports tokens from `@flyee/design-tokens/css/*`; never recreate tokens locally.
- Deploys go ONLY through GitHub Actions (`.github/workflows/deploy.yml`: `vercel pull/build/deploy --prebuilt`); the Vercel Git integration stays disconnected. Runbook: `docs/DEPLOY.md`.
- Server-only secrets (`DATABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, provider keys) never reach client components.
- `apps/web/.env` holds inherited MedChina production credentials and `apps/web/.env.local` blanks them; keep `.env.local` until the flyee.club services exist (root `CLAUDE.md`, "Safety during the transition").
